General

What is the FCS CLI?

The CrowdStrike Falcon Cloud Security (FCS) CLI is a command-line tool that lets you scan container images and Infrastructure as Code (IaC) configurations for vulnerabilities and misconfigurations using the CrowdStrike Falcon platform.

It integrates directly with the Falcon API, so scan results feed into the same Falcon console where the rest of your security posture lives — enabling a unified view across cloud workloads, containers, and IaC templates.

What can the FCS CLI do?

The FCS CLI supports two primary scan types:

  • Container image scanning — Scans Docker images for known CVEs, vulnerable packages, and OS-level vulnerabilities. Works with public images and private registries (ECR, GCR, ACR, Docker Hub, etc.).
  • Infrastructure as Code (IaC) scanning — Detects security misconfigurations in Terraform, Kubernetes manifests, CloudFormation templates, and other IaC formats.

Beyond scanning, it supports multiple output formats (JSON, SARIF, human-readable), profile-based configuration, batch operations, and self-updating.

What CrowdStrike subscription or license is required?

You need an active CrowdStrike Falcon subscription that includes Falcon Cloud Security.

Falcon Console Required — The FCS CLI binary is downloaded from the Falcon console. Navigate to Cloud Security → Image Assessment → CI/CD Integrations. You must be logged in with an account that has access to Falcon Cloud Security.

You also need a CrowdStrike API client with the appropriate scopes for the features you plan to use. See the Authentication & Configuration section for the required scopes.

What platforms and architectures are supported?
PlatformArchitectures

Is the FCS CLI open source?

No. The FCS CLI binary itself is proprietary CrowdStrike software and is not open source. However, this example repository — including all scripts, workflow templates, and documentation — is released under the MIT license and is freely usable and modifiable.

Installation

What are the different ways to install the FCS CLI?

There are four installation methods:

  1. Manual download from Falcon console — Download the binary directly from the Falcon console and place it on your PATH. Requires Falcon console access — see How do I manually download the FCS CLI from the Falcon console? below.
  2. Assisted install script — An install script (install-fcs-cli.sh) is available in the repository that auto-detects your platform and architecture, downloads the correct binary via the Falcon API, and handles placement automatically. Requires the Cloud Security Tools Download: Read API scope.
  3. Programmatic API download — Authenticate with the Falcon API to download the binary without console access. Best for CI/CD pipelines. Requires valid API credentials with the Cloud Security Tools Download: Read scope.
  4. Self-update — If the CLI is already installed, run fcs update to update to the latest version in-place. Also requires the Cloud Security Tools Download: Read scope.
How do I manually download the FCS CLI from the Falcon console?
Falcon Console Required — Navigate to Cloud Security → Image Assessment → CI/CD Integrations to access the binary download.

Once downloaded, move the binary to a directory on your PATH and make it executable:

# macOS / Linux
chmod +x fcs
sudo mv fcs /usr/local/bin/

# Verify
fcs --help

Choose the correct binary for your platform and architecture from the download page:

PlatformArchitecture
Linuxamd64 or arm64
macOSamd64 (Intel) or arm64 (Apple Silicon)
Windowsamd64 or arm64
How do I download the CLI programmatically via the API?

Use the Falcon OAuth2 token endpoint to get a bearer token, then call the sensor download API to retrieve the binary. This approach works without console access and is ideal for CI/CD pipelines.

# Step 1: Get an OAuth2 token
TOKEN=$(curl -s -X POST https://api.crowdstrike.com/oauth2/token \
  -d "client_id=${FALCON_CLIENT_ID}&client_secret=${FALCON_CLIENT_SECRET}" \
  | jq -r '.access_token')

# Step 2: List available FCS CLI versions
curl -s -H "Authorization: Bearer ${TOKEN}" \
  "https://api.crowdstrike.com/sensor-installers/entities/versions/v1?type=fcs" \
  | jq '.resources[].version'

# Step 3: Download the binary for your platform
curl -sL -H "Authorization: Bearer ${TOKEN}" \
  "https://api.crowdstrike.com/sensor-installers/entities/download/v2?type=fcs&os=linux&arch=amd64" \
  -o fcs && chmod +x fcs

Replace os and arch with values matching your target platform (linux/darwin/windows, amd64/arm64).

Requirements: curl and jq must be installed. The API client needs the Cloud Security Tools Download: Read scope.
Non-US-1 regions: Replace api.crowdstrike.com with your regional API endpoint (e.g., api.us-2.crowdstrike.com).
How do I verify my installation?

Run either of these commands after installation:

fcs --help
fcs --version

If the command is not found, ensure the install directory is on your PATH. For example, if you installed to /usr/local/bin:

export PATH="/usr/local/bin:$PATH"
# Add the above line to your ~/.zshrc or ~/.bashrc to make it permanent
How do I update the FCS CLI to the latest version?

If the CLI is already installed and configured, run the built-in update command:

fcs update

This downloads and replaces the binary in-place. The API client used must have the Cloud Security Tools Download: Read scope enabled.

In CI/CD pipelines, prefer pinning a specific version using the download script rather than relying on fcs update, to ensure reproducible builds.

Authentication & Configuration

What API credentials do I need?

You need a CrowdStrike API client with a Client ID and Client Secret.

Falcon Console Required — Create API clients in the Falcon console under Support & Resources → API Clients & Keys → Add new API client. You must have the appropriate role permissions to create API clients.

Assign only the scopes your use case requires:

FeatureRequired API Scopes
Container Image ScanningFalcon Container CLI: Read/Write
Falcon Container Image: Read/Write
IaC ScanningInfrastructure as Code: Read/Write
CLI Updates (fcs update)Cloud Security Tools Download: Read
Best practice: Create separate API clients for each environment (dev, staging, prod) and grant only the minimum scopes needed.
How do I configure the CLI for the first time?
Falcon Console Required — Before configuring the CLI, you need your API Client ID and Secret. Obtain these from Support & Resources → API Clients & Keys in the Falcon console.

Run the interactive setup wizard:

fcs configure

Or configure non-interactively (useful for scripts and CI/CD):

fcs configure \
  --client-id YOUR_CLIENT_ID \
  --client-secret YOUR_CLIENT_SECRET \
  --falcon-cloud us-1

This creates a configuration file at ~/.crowdstrike/fcs.json.

Where is the configuration file stored?

The configuration file is stored at:

~/.crowdstrike/fcs.json

This location is XDG-compliant and contains your credentials and profiles in JSON format. Ensure this file has restrictive permissions (600) so other users on the system cannot read your credentials.

How does credential precedence work?

When the CLI looks for credentials, it checks in this order (highest priority first):

  1. CLI flags — --client-id and --client-secret passed directly
  2. Environment variables — FALCON_CLIENT_ID, FALCON_CLIENT_SECRET, FALCON_CLOUD
  3. Named profile — The profile specified with --profile <name>
  4. Default profile — The profile marked as default in ~/.crowdstrike/fcs.json

This means environment variables always override the config file, which is the recommended pattern for CI/CD systems.

How do I set up multiple profiles for different environments?

Create named profiles for each environment during configuration:

# Create a production profile
fcs configure --profile production \
  --client-id PROD_CLIENT_ID \
  --client-secret PROD_CLIENT_SECRET \
  --falcon-cloud us-1

# Create a staging profile
fcs configure --profile staging \
  --client-id STAGING_CLIENT_ID \
  --client-secret STAGING_CLIENT_SECRET \
  --falcon-cloud us-1

Then select the profile at scan time:

fcs --profile production scan image nginx:latest
fcs --profile staging scan image myapp:dev

How should I handle credentials in CI/CD environments?

Always store API credentials as encrypted secrets in your CI/CD platform — never hardcode them in workflow files or scripts.

  • GitHub Actions: Store as repository or organization secrets, then expose as env vars in your workflow.
  • GitLab CI: Use project-level CI/CD variables (masked and protected).
  • Jenkins: Use the Credentials Store with a Secret Text credential type.

The CLI picks up credentials from environment variables automatically, so no config file is needed in CI:

env:
  FALCON_CLIENT_ID: ${{ secrets.FALCON_CLIENT_ID }}
  FALCON_CLIENT_SECRET: ${{ secrets.FALCON_CLIENT_SECRET }}
  FALCON_CLOUD: us-1

Image Scanning

How do I scan a Docker image?

Use the scan image subcommand followed by the image reference:

# Scan a public image (latest tag)
fcs scan image nginx:latest

# Scan a specific version
fcs scan image python:3.11-slim

# Scan by image digest (most reproducible)
fcs scan image nginx@sha256:abc123...

The CLI connects to your local Docker daemon to pull and analyze the image, then submits it to the Falcon API for vulnerability assessment.

How do I scan images from private registries?

Authenticate with your registry using docker login first, then scan by referencing the full image path:

# Docker Hub private repo
docker login
fcs scan image myorg/private-app:1.0

# AWS ECR
aws ecr get-login-password --region us-east-1 | \
  docker login --username AWS --password-stdin 123456789.dkr.ecr.us-east-1.amazonaws.com
fcs scan image 123456789.dkr.ecr.us-east-1.amazonaws.com/myapp:latest

# Google Container Registry
gcloud auth configure-docker
fcs scan image gcr.io/my-project/myapp:latest

# Azure Container Registry
az acr login --name myregistry
fcs scan image myregistry.azurecr.io/myapp:latest

The CLI uses your existing Docker credentials, so any registry Docker can pull from is supported.

What timeout should I use for large images?

The default timeout may not be sufficient for large images. Use the --timeout flag (value in seconds):

Image SizeRecommended Timeout
Small (< 200MB)120s (default)
Medium (200MB–1GB)300s
Large (> 1GB)600s+
fcs scan image --timeout 600 large-image:latest

If you consistently hit timeouts, check network bandwidth to the Falcon API endpoint and consider scanning during off-peak hours.

How do I configure a custom Docker socket?

By default, the CLI connects to /var/run/docker.sock. Override this with the FCS_SOCKET environment variable or the --socket flag:

# Unix socket (non-default path)
export FCS_SOCKET=/run/user/1000/docker.sock
fcs scan image myapp:latest

# TCP socket
export FCS_SOCKET=tcp://localhost:2376

# Windows named pipe
export FCS_SOCKET=npipe:////./pipe/docker_engine
Can I scan an image that hasn't been pushed to a registry?

Yes. If the image exists in your local Docker daemon (e.g., just built with docker build), the CLI can scan it directly by its local tag — no registry push required.

# Build an image
docker build -t myapp:dev .

# Scan it immediately
fcs scan image myapp:dev

This makes it easy to shift security scanning left — scan before you push.

How do I enable verbose/debug output for a scan?

Use the --verbose flag, or set FCS_DEBUG=true for detailed API-level logging:

# Verbose mode
fcs --verbose scan image nginx:latest

# Debug mode (API calls, full response payloads)
FCS_DEBUG=true fcs scan image nginx:latest

Verbose output is useful for understanding what's happening during a scan. Debug mode is helpful when troubleshooting authentication or connectivity issues.

IaC Scanning

What IaC file types are supported?

The FCS CLI supports scanning the following Infrastructure as Code formats:

  • Terraform — .tf files and directories
  • Kubernetes — YAML manifests (deployment.yaml, pod.yaml, etc.)
  • CloudFormation — AWS CloudFormation templates (YAML or JSON)
  • Additional IaC types may be supported — check the Falcon console for the latest list.

The CLI detects IaC types automatically based on file contents, so you typically don't need to specify the type explicitly.

How do I scan a Terraform directory?

Point fcs scan iac at the directory containing your .tf files:

# Scan current directory
fcs scan iac .

# Scan a specific path
fcs scan iac ./terraform/environments/production

# Output as JSON
fcs scan iac ./terraform --output json

The CLI recursively scans all .tf files under the specified path.

How do I scan Kubernetes manifests?

Pass the path to your manifest directory or a single file:

# Scan all manifests in a directory
fcs scan iac ./kubernetes/

# Scan a single manifest
fcs scan iac deployment.yaml

# Common issues it detects in Kubernetes:
# - Privileged containers
# - Missing resource limits
# - Containers running as root
# - Writable root filesystems
# - Missing network policies
Can I scan multiple IaC types in a single command?

Yes. Point the command at a directory that contains multiple IaC types and the CLI will detect and scan all of them:

# Scan a repo root containing Terraform, Kubernetes, and CloudFormation
fcs scan iac ./infrastructure/

Results will be grouped by resource type in the output, making it easy to see issues across your entire infrastructure footprint.

How do I use IaC scanning as a pre-commit git hook?

Add the following to .git/hooks/pre-commit (and make it executable with chmod +x):

#!/bin/bash
# Pre-commit hook: scan IaC changes before committing
STAGED_IAC=$(git diff --cached --name-only | grep -E '\.(tf|yaml|yml|json)$')

if [ -n "$STAGED_IAC" ]; then
  echo "Running FCS IaC scan on staged files..."
  fcs scan iac . --output json | \
    jq -r '.issues[] | select(.severity == "CRITICAL") | .message' | \
    while read line; do
      echo "CRITICAL: $line"
      exit 1
    done
fi

This blocks commits when critical IaC issues are detected in staged files.

Output & Reporting

What output formats are available?

The FCS CLI supports three output formats:

  • Human-readable (default) — Formatted text output suitable for terminal review
  • JSON (--output json) — Machine-readable structured output, ideal for piping to jq or storing as artifacts
  • SARIF (--output sarif) — Static Analysis Results Interchange Format, used by GitHub Advanced Security and other SAST tools
fcs scan image nginx:latest --output json > results.json
fcs scan image nginx:latest --output sarif > results.sarif
How do I parse scan results with jq? 
# Count vulnerabilities by severity
fcs scan image nginx:latest --output json | \
  jq '[.vulnerabilities[].severity] | group_by(.) | map({(.[0]): length}) | add'

# List only critical vulnerabilities
fcs scan image nginx:latest --output json | \
  jq '.vulnerabilities[] | select(.severity == "CRITICAL") | {cve: .cve_id, package: .package_name}'

# Get total vulnerability count
fcs scan image nginx:latest --output json | \
  jq '.vulnerabilities | length'

# Check if any fixable criticals exist
fcs scan image nginx:latest --output json | \
  jq '[.vulnerabilities[] | select(.severity == "CRITICAL" and .fix_available == true)] | length'
How do I upload scan results to GitHub's Security tab?

Output results in SARIF format, then use the github/codeql-action/upload-sarif action:

- name: Run FCS image scan
  run: fcs scan image ${{ env.IMAGE }} --output sarif > results.sarif

- name: Upload SARIF to GitHub Security
  uses: github/codeql-action/upload-sarif@v3
  with:
    sarif_file: results.sarif
  if: always()  # Upload even if scan finds issues

Results will appear in the Security → Code scanning alerts tab of your repository.

How do I generate an HTML report from scan results?

Save the scan results as JSON, then use jq to transform them into an HTML report:

# Save JSON results
fcs scan image nginx:latest --output json > scan-results.json

# Extract summary fields to build a report
jq -r '
  "",
  "
FCS Scan Report
",
  "
Image: " + .image + "
",
  "
Total vulnerabilities: " + (.vulnerabilities | length | tostring) + "
",
  "",
  ([.vulnerabilities[].severity] | group_by(.) | map(
    ""
  ) | .[]),
  "
SeverityCount
" + .[0] + "" + (length | tostring) + "
"
' scan-results.json > report.html

For richer reporting, consider piping the JSON output to a dedicated SAST reporting tool, or uploading SARIF output to GitHub Advanced Security for integrated vulnerability tracking.

Requirement: jq must be installed for JSON parsing.
How do I archive scan results as CI/CD artifacts?

In GitHub Actions, use the actions/upload-artifact action after scanning:

- name: Scan image
  run: |
    mkdir -p scan-results
    fcs scan image $IMAGE --output json > scan-results/image-scan.json
    fcs scan iac ./terraform --output json > scan-results/iac-scan.json

- name: Archive scan results
  uses: actions/upload-artifact@v4
  if: always()
  with:
    name: security-scan-results
    path: scan-results/
    retention-days: 30

CI/CD Integration

How do I integrate the FCS CLI with GitHub Actions?

Store your Falcon API credentials as encrypted repository secrets (FALCON_CLIENT_ID, FALCON_CLIENT_SECRET), then download and run the CLI in your job steps.

Falcon Console Required — Your API credentials must first be created in the Falcon console under Support & Resources → API Clients & Keys.

A minimal GitHub Actions job looks like this:

jobs:
  security-scan:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Download FCS CLI
        env:
          FALCON_CLIENT_ID: ${{ secrets.FALCON_CLIENT_ID }}
          FALCON_CLIENT_SECRET: ${{ secrets.FALCON_CLIENT_SECRET }}
          FALCON_CLOUD: us-1
        run: |
          TOKEN=$(curl -s -X POST https://api.crowdstrike.com/oauth2/token \
            -d "client_id=${FALCON_CLIENT_ID}&client_secret=${FALCON_CLIENT_SECRET}" \
            | jq -r '.access_token')
          curl -sL -H "Authorization: Bearer ${TOKEN}" \
            "https://api.crowdstrike.com/sensor-installers/entities/download/v2?type=fcs&os=linux&arch=amd64" \
            -o fcs && chmod +x fcs && sudo mv fcs /usr/local/bin/

      - name: Scan image
        env:
          FALCON_CLIENT_ID: ${{ secrets.FALCON_CLIENT_ID }}
          FALCON_CLIENT_SECRET: ${{ secrets.FALCON_CLIENT_SECRET }}
          FALCON_CLOUD: us-1
        run: fcs scan image myapp:${{ github.sha }}
How do I cache the FCS CLI binary in GitHub Actions?

Use actions/cache keyed on the CLI version to avoid re-downloading on every run:

- name: Cache FCS CLI
  uses: actions/cache@v4
  id: cache-fcs
  with:
    path: /usr/local/bin/fcs
    key: fcs-cli-${{ runner.os }}-${{ env.FCS_VERSION }}

- name: Download FCS CLI
  if: steps.cache-fcs.outputs.cache-hit != 'true'
  env:
    FALCON_CLIENT_ID: ${{ secrets.FALCON_CLIENT_ID }}
    FALCON_CLIENT_SECRET: ${{ secrets.FALCON_CLIENT_SECRET }}
    FALCON_CLOUD: us-1
  run: |
    TOKEN=$(curl -s -X POST https://api.crowdstrike.com/oauth2/token \
      -d "client_id=${FALCON_CLIENT_ID}&client_secret=${FALCON_CLIENT_SECRET}" \
      | jq -r '.access_token')
    curl -sL -H "Authorization: Bearer ${TOKEN}" \
      "https://api.crowdstrike.com/sensor-installers/entities/download/v2?type=fcs&os=linux&arch=amd64" \
      -o fcs && chmod +x fcs && sudo mv fcs /usr/local/bin/

This is especially valuable in matrix builds scanning multiple images, where the binary would otherwise be downloaded once per matrix entry.

How do I gate a pipeline based on scan results?

Scan with JSON output, use jq to extract severity counts, and fail the pipeline with a non-zero exit code when thresholds are exceeded:

# Scan and evaluate
fcs scan image myapp:latest --output json > results.json

CRITICAL=$(jq '[.vulnerabilities[] | select(.severity=="CRITICAL")] | length' results.json)
HIGH=$(jq '[.vulnerabilities[] | select(.severity=="HIGH")] | length' results.json)

if (( CRITICAL > 0 )); then
  echo "Build blocked: $CRITICAL critical vulnerabilities found"
  exit 1
fi

if (( HIGH > 5 )); then
  echo "Build blocked: $HIGH high-severity issues exceed threshold of 5"
  exit 1
fi

echo "Security gate passed."

To warn without blocking during a gradual rollout, replace exit 1 with a logged warning and exit 0. Tighten the thresholds once teams have addressed the backlog.

How do I integrate with Jenkins?

Use the Jenkins Credentials Store for secrets and a declarative pipeline. The CLI is downloaded at runtime using the Falcon API:

Falcon Console Required — Create your API credentials in the Falcon console under Support & Resources → API Clients & Keys, then store the Client ID and Secret in the Jenkins Credentials Store as Secret Text entries.
pipeline {
    agent any
    environment {
        FALCON_CLIENT_ID = credentials('falcon-client-id')
        FALCON_CLIENT_SECRET = credentials('falcon-client-secret')
        FALCON_CLOUD = 'us-1'
    }
    stages {
        stage('Download FCS CLI') {
            steps {
                sh '''
                  TOKEN=$(curl -s -X POST https://api.crowdstrike.com/oauth2/token \
                    -d "client_id=${FALCON_CLIENT_ID}&client_secret=${FALCON_CLIENT_SECRET}" \
                    | jq -r '.access_token')
                  curl -sL -H "Authorization: Bearer ${TOKEN}" \
                    "https://api.crowdstrike.com/sensor-installers/entities/download/v2?type=fcs&os=linux&arch=amd64" \
                    -o fcs && chmod +x fcs
                '''
            }
        }
        stage('Security Scan') {
            steps {
                sh './fcs scan image ${IMAGE_NAME}:${BUILD_NUMBER} --output json > results.json'
            }
            post {
                always {
                    archiveArtifacts artifacts: 'results.json'
                }
            }
        }
    }
}

Advanced Features

How do I scan multiple images in batch?

Create a text file with one image per line (lines starting with # are treated as comments), then loop over it in a shell script:

# images.txt
nginx:latest
redis:7-alpine
python:3.11-slim
# Comments are supported
node:20-alpine
mkdir -p scan-results

while IFS= read -r image || [[ -n "$image" ]]; do
  # Skip blank lines and comments
  [[ -z "$image" || "$image" == \#* ]] && continue
  echo "Scanning: $image"
  safe_name=$(echo "$image" | tr '/:' '--')
  fcs scan image "$image" --output json > "scan-results/${safe_name}.json"
done < images.txt

To run scans in parallel, use & with a concurrency limit:

MAX_PARALLEL=4
count=0
while IFS= read -r image || [[ -n "$image" ]]; do
  [[ -z "$image" || "$image" == \#* ]] && continue
  fcs scan image "$image" --output json > "scan-results/$(echo $image | tr '/:' '--').json" &
  (( count++ ))
  (( count % MAX_PARALLEL == 0 )) && wait
done < images.txt
wait
How do I scan all Docker images currently in my local daemon?

Use docker image ls to enumerate local images, then loop through and scan each one:

# List all local images and scan each one
docker image ls --format '{{.Repository}}:{{.Tag}}' \
  | grep -v '' \
  | while read image; do
    echo "Scanning: $image"
    safe_name=$(echo "$image" | tr '/:' '--')
    fcs scan image "$image" --output json > "scan-results/${safe_name}.json"
  done
Note: On systems with many images this can take significant time. The grep -v '<none>' filter skips untagged intermediate layers.
How do I run scans in parallel?

Both batch scan scripts support a --parallel flag that sets the maximum number of concurrent scans:

# Run up to 4 scans concurrently
./scripts/batch-scan-images.sh --parallel 4 images.txt
Tip: Parallelism is limited by available CPU, network bandwidth to the Falcon API, and your API rate limits. Start with 2–4 and tune from there. Avoid setting this too high in shared CI environments.
How do I add logging and retry logic to scans for production use?

For production cron jobs and scheduled automation, wrap the fcs command with retry logic, timestamped logging, and failure alerting. Here's a minimal pattern:

#!/bin/bash
set -euo pipefail

LOG_FILE="/var/log/fcs/scan-$(date +%Y%m%d-%H%M%S).log"
MAX_RETRIES=3
RETRY_DELAY=30

run_with_retry() {
  local attempt=1
  until fcs "$@" 2>&1 | tee -a "$LOG_FILE"; do
    if (( attempt >= MAX_RETRIES )); then
      echo "FAILED after $MAX_RETRIES attempts" | tee -a "$LOG_FILE"
      # Optionally: send Slack/PagerDuty alert here
      exit 1
    fi
    echo "Attempt $attempt failed. Retrying in ${RETRY_DELAY}s..." | tee -a "$LOG_FILE"
    (( attempt++ ))
    sleep "$RETRY_DELAY"
  done
}

run_with_retry scan image nginx:latest --output json

Key additions for production readiness:

  • Logging — Tee output to a timestamped file for audit trails
  • Retries — Handle transient API timeouts gracefully
  • Alerting — Post to Slack via webhook or trigger PagerDuty on persistent failure
  • Exit codes — Use set -e to propagate failures to cron/scheduling systems
How do I scan images across multiple CrowdStrike regions?

Run the same scan against each region's API endpoint by switching the FALCON_CLOUD environment variable (or --falcon-cloud flag) between runs:

mkdir -p multi-region-results

for region in us-1 us-2 eu-1; do
  echo "Scanning against region: $region"
  FALCON_CLOUD=$region fcs scan image nginx:latest \
    --output json > "multi-region-results/${region}.json"
done

# Compare critical counts across regions
for f in multi-region-results/*.json; do
  region=$(basename "$f" .json)
  count=$(jq '[.vulnerabilities[] | select(.severity=="CRITICAL")] | length' "$f")
  echo "$region: $count critical"
done

If you have separate API credentials per region, use different profiles or set FALCON_CLIENT_ID and FALCON_CLIENT_SECRET per loop iteration.

Falcon Console Required — Each region requires its own API credentials created in the corresponding regional Falcon console instance. Ensure you log in to the correct regional console when creating each set of credentials.
How do I enforce severity-based security policies?

Run the scan with JSON output, then use jq to extract counts and apply thresholds in shell:

# Scan and save results
fcs scan image myapp:latest --output json > results.json

# Count by severity
CRITICAL=$(jq '[.vulnerabilities[] | select(.severity=="CRITICAL")] | length' results.json)
HIGH=$(jq '[.vulnerabilities[] | select(.severity=="HIGH")] | length' results.json)
MEDIUM=$(jq '[.vulnerabilities[] | select(.severity=="MEDIUM")] | length' results.json)

echo "Critical: $CRITICAL | High: $HIGH | Medium: $MEDIUM"

# Enforce thresholds — exit 1 to fail a CI pipeline
if (( CRITICAL > 0 )); then
  echo "POLICY VIOLATION: $CRITICAL critical vulnerabilities found"
  exit 1
fi

if (( HIGH > 10 )); then
  echo "POLICY VIOLATION: $HIGH high vulnerabilities exceed limit of 10"
  exit 1
fi

echo "Policy check passed."

The same pattern works for IaC scan results — replace .vulnerabilities[] with the appropriate field path from the IaC JSON output (.issues[]).

Troubleshooting

I'm getting an authentication error — what should I check?

Work through this checklist:

  1. Verify credentials — Confirm the Client ID and Secret are correct and haven't been revoked.
  2. Check the region — The most common cause. Your configured region must match your Falcon console URL. A us-2 tenant using us-1 credentials will always fail.
  3. Check API scopes — Ensure the API client has the required scopes for the operation you're performing.
  4. Check for env var conflicts — Run env | grep FALCON to see if stale environment variables are overriding your config file.
  5. Enable debug mode — Run with FCS_DEBUG=true to see the full API request/response for more details.
I'm getting a "context deadline exceeded" error — what does that mean?

This is a timeout error — the scan took longer than the configured timeout allows. Fix it by increasing the timeout:

# For a large image
fcs scan image --timeout 600 large-image:latest

# Set a default in the environment
export FCS_TIMEOUT=600

If you're still hitting timeouts after increasing to 600s+, check:

  • Network latency to the Falcon API endpoint
  • Whether the Docker pull itself is slow (large image on a slow connection)
  • Whether the CI runner has restricted egress bandwidth
The "fcs" command is not found after installation

The binary is installed but its directory isn't on your PATH. First, find where it was installed:

find /usr/local /opt /home -name 'fcs' 2>/dev/null

Then add that directory to your PATH. For example, if it's in /usr/local/bin:

# Add to ~/.zshrc or ~/.bashrc
export PATH="/usr/local/bin:$PATH"

# Reload
source ~/.zshrc

To avoid this in future installs, use --install-dir to specify a directory that's already on your PATH:

./scripts/install-fcs-cli.sh --install-dir /usr/local/bin
I can't connect to the Docker daemon during a scan

The CLI connects to Docker via the socket at /var/run/docker.sock by default. Common causes and fixes:

  • Docker isn't running — Start the Docker daemon: sudo systemctl start docker
  • Permission denied — Add your user to the docker group: sudo usermod -aG docker $USER, then re-login.
  • Non-standard socket path — Specify the socket explicitly: export FCS_SOCKET=/custom/path/docker.sock
  • In CI with Docker-in-Docker — Set FCS_SOCKET=tcp://docker:2375 if using DinD.
How do I enable debug logging for detailed troubleshooting?

Two levels of additional logging are available:

# Verbose: human-readable scan progress detail
fcs --verbose scan image nginx:latest

# Debug: full API request/response payloads
FCS_DEBUG=true fcs scan image nginx:latest

# Both together
FCS_DEBUG=true fcs --verbose scan image nginx:latest 2>&1 | tee debug.log

Capture to a file and share the output when filing a support ticket or reporting an issue.

Scans work locally but fail in CI — how do I diagnose this?

The most common causes of CI-only failures:

  • Missing or wrong secrets — Verify that FALCON_CLIENT_ID and FALCON_CLIENT_SECRET are set and the values are correct. Check that secret masking isn't corrupting the value (some CI systems mask partial matches).
  • Wrong region — Ensure FALCON_CLOUD is set to the correct region in your CI environment.
  • No Docker daemon — CI runners often need Docker-in-Docker or a Docker socket mount. Verify with docker info in a preceding step.
  • Egress blocked — Check if your CI runner has outbound HTTPS access to api.crowdstrike.com (or your regional endpoint).
  • Timeout too short — CI runners can have slower network throughput. Increase --timeout.

Add FCS_DEBUG=true to your CI environment variables temporarily to get full diagnostic output.
